# PostgreSQL roles and tenant context

Apply versioned migrations with a dedicated login assigned the `musclecuties_migrator` group and set connection option `Options=-c role=musclecuties_migrator`. The migration login must not be a superuser or have `BYPASSRLS`; row security is forced on the account and tenant tables, including for their owner. Runtime data connections use a separate login assigned to `musclecuties_app` with `Options=-c role=musclecuties_app`; authentication uses a separate login with `Options=-c role=musclecuties_auth`. These group-role settings ensure `current_user` inside RLS and the auth lookup policy names the least-privilege role.

Run `roles-and-grants.sql` as a PostgreSQL administrator after the migrations. Provision secret-bearing login roles through the deployment secret manager and grant them membership in the appropriate group. The runtime data group can read `catalog`, read and modify only tenant tables protected by RLS, and cannot access global email challenges, operations logs, migration history, or schema ownership. Authentication uses the separate `musclecuties_auth` group: it can call `app.lookup_user_by_email(email)` or `app.lookup_user_by_apple_id(subject)` to retrieve the minimal login fields for one account and can use the email challenge table. Each function runs as the migration owner and is constrained by the migration-owner-only RLS policy; the auth role has no direct access to `app.users`. It cannot access tenant tables, catalog data or operations logs.

Resolve the tenant UUID from authenticated server-side identity. Start a database transaction, call `PostgresTenantContext.SetForCurrentTransactionAsync(context, authenticatedUserId, cancellationToken)`, perform the operation and save changes, then commit. This uses PostgreSQL `set_config(..., true)`, which is transaction-local; committing or rolling back clears the setting before the connection returns to the pool. Never accept the tenant UUID from an untrusted request body or use session-level `SET`.

Because the provider enables transient retries, callers that open explicit transactions must execute the complete transaction delegate under EF Core's configured execution strategy. Operations with externally visible effects also need the PG02-05 idempotency key before retrying an ambiguous commit.
