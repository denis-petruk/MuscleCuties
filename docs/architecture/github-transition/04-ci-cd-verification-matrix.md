# CI/CD verification and acceptance matrix

Proposed gates, 2026-11-04. **No application test, MAUI build/run, load test or deployment was executed in this planning task.** Existing checked-in results are historical evidence at their source/date. A gate passes only for the exact candidate/target with attached output. `NOT RUN`, `NOT VERIFIED`, `FAIL`, and `BLOCKED` never count as PASS. No fixture on Beta is disposable merely because its resource name says staging.

Use [G0–G9](../../VERIFICATION_GATES.md) for risk/evidence semantics. This document adds environment/release acceptance without redefining those gates. Work package dependencies are in the [roadmap](03-implementation-roadmap.md).

## Quantitative gates and evidence retention

The current local diagnostic budget is 1000ms in docs/performance; it is not an approved end-to-end planner SLO. Before P10 qualification, I/O approve per-route success-path latency/error/throughput targets, representative request size/history/catalog, concurrency, sample counts, cold/warm classification and observation window. Fix the historic failure or produce new attributable evidence; do not lower the bar after seeing results without a recorded owner decision. Beta observation must fit real traffic and privacy constraints.

Record release/source/tree/artifact/config/schema and supported-client identities; exact commands/runners/results and failed/skipped totals; synthetic scenario IDs and timestamps; reviewer/approval/lease; measured errors/latency/pending age; pre/post alias and migration state; recovery results. Preserve TRX/build evidence 30 days and release/migration/approval evidence at least through the owner-agreed rollback/audit retention period (existing CI uses 90 days for deployment reports; longer policy remains an owner decision). Keep secrets, user rows, tokens and photos out of artifacts. Use access-controlled operational evidence for protected data-plane metadata; source docs link sanitized summaries.
