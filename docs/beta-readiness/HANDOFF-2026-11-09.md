## In-session swap: fixed in `e0adcaf9` (keep as the defect record)

> **Resolved.** `source_exercise_id` is persisted on `catalog.workout_exercise_definitions` (migration 006) and both
> directions translate through it; all three guards pass (3 passed, 0 skipped). Read the analysis below before changing
> the swap id contract again, because the contract is definition ids and the translation is the invariant.

Measured on the seeded disposable database (catalog lives in schema `catalog`, not `public`):

```
catalog.exercises                    104 rows   ENGINE_141 → id 31, ENGINE_142 → id 32
catalog.workout_exercise_definitions  60 rows   ids 1..60, seed_code = urn:musclecuties:seed:v1:<guid>
                                               no ENGINE_* seed code, no rows 141/142
```

The two id spaces are deliberate and are already translated once, at import time:

- `WorkoutExerciseV020CatalogMapper.Map` builds `ReviewedExerciseCandidate(definition.Id, …)`, so the eligibility rule
  and every candidate speak **definition ids**.
- `PostgresReviewedExerciseCatalogImporterV020.ApplyAsync` builds `databaseIdBySourceId` from
  `exercises[].sourceExerciseId` → `bySeedCode[seedCode].Id`, and `EvidenceJson` rewrites `targetSourceExerciseId` into
  that definition id. `ReviewedSubstituteExerciseIdsV020Json` is always `"[]"`; the reviewed pairs live in
  `ReviewEvidenceV020Json.resolvedDirectedSubstitutionReviews[].targetExerciseId`.

The store then mixes the spaces:

1. `GetSwapCandidatesAsync` (`PostgresWorkoutPlanAndSessionStore.cs`, ~750-840) computes
   `currentPlanningId = ExtractPlanningId(catalogExercise.Code)` → `142`, a **source** id, then looks up
   `allDefinitions.FirstOrDefault(d => d.Id == currentPlanningId.Value)`. Definition ids are 1..60, so this is always
   null and the method returns `[]` — **the swap sheet never offers a candidate for any real plan**.
2. `SwapAsync` (~845-940) resolves `newExerciseDef` by `Id == request.NewExerciseId` (definition id, consistent with
   what candidates return), but passes the day exercise's *source* id to `EvaluateAsync` as `originalExerciseId`, so the
   original exercise is unreachable and a real request cannot pass eligibility.
3. `targetCode = $"ENGINE_{request.NewExerciseId}"` with the fallback `|| e.Id == request.NewExerciseId` can assign the
   **wrong catalog row**: `ENGINE_31` does not exist, and the fallback matches `catalog.exercises.id = 31`, which is
   `ENGINE_141` (Pull-Up). Do not keep that fallback.

The two skipped tests in `WorkoutSwapAndRescheduleSafetyTests` post `NewExerciseId = 141/142`, i.e. the source space.
That is a contract decision, not a fixture detail. Recommended: keep the swap API in definition ids (what candidates
already return) and translate exactly once at the boundary.

Recommended shape — a schema change, so it needs owner review and a migration ledger entry: persist
`source_exercise_id` on `catalog.workout_exercise_definitions`, backfill from the reviewed JSON, translate at the
boundary, derive `targetCode` from the source id. Follow expand → compatible backend → deferred contract; `dbinit` is
not a drift repair and no runtime/cold-start migration may be introduced.

Third guard: `RescheduleMovesTheWholeOccurrenceAndRejectsAThirdActivityOnADay` fails closed with
`ScheduleStrengthMuscleMetadataMissing` because the synthetic `WorkoutDayExerciseRecord` carries no reviewed muscle
metadata. The guard is behaving correctly — seed the metadata.
