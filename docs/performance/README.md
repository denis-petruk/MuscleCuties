# Server latency report

**Measured:** 2026-11-03T12:59:05Z  
**Environment:** in-process ASP.NET TestServer, .NET 10.0.14, macOS 26.6.2  
**Database:** disposable PostgreSQL 17 fixture (`mc_test_nutrition_ci`)  
**Budget:** 1000 ms for the handler cold request and for warm p95

The in-process machine-readable report is [server-latency-report.json](server-latency-report.json); the deployed staging measurement is [deployed-latency-report.json](deployed-latency-report.json). The local report is generated by `ServerRouteParityTests.EveryMappedRouteHasMeasuredColdAndWarmP95WithinBudget`, which enumerates the live `EndpointDataSource` — the same map used by the route guard — and fails when a route is missing from this report, when a report entry carries a different procedure, or when any route exceeds the budget.

## Reproduce it

One command writes the report and fails the build when the gate is not green:

```bash
MC_LATENCY_POSTGRES='Host=127.0.0.1;Port=55432;Database=mc_test_nutrition_ci;Username=postgres;Password=<fixture-password>' \
  bash scripts/measure-server-latency.sh
```

The script uses the repository's pinned SDK at `/tmp/dotnet-10.0.403` unless `DOTNET_ROOT` is already set. It requires the disposable PostgreSQL fixture.

## Protocol

- **Startup / readiness (`host-start-plus-live-readiness-v1`):** a fresh host is built and started, then called once at `GET /health/live` with a bounded 30 s wait. The elapsed time is recorded per route as `StartupMs`. It is reported separately and is **not** added to `ColdMs`. `/health/live` is a constant liveness response; it does not query PostgreSQL or the measured route.
- **Cold (`fresh-host-first-request-v1`):** the first request to the measured route after readiness on that same fresh host. Hosts are created and measured sequentially, one route at a time, so no route's startup or JIT work is charged to another. The request has a per-request 1000 ms cancellation limit. Status `0` means the request reached that limit.
- **Warm p95 (`shared-host-20-sample-p95-v1`):** 20 requests to the route on one shared host; the 95th percentile is reported.
- **Database:** every route uses the disposable PostgreSQL fixture, not the synthetic unreachable connection used by the general server tests.
- **External boundary:** photo routes are exercised through their server-side handler only. S3 presigning is not contacted; the report labels those routes `ExternalDependency`. Deployed Lambda cold starts and p99 on the only deployed backend are measured separately below; they are not folded into these local numbers.
- **Status codes:** requests use synthetic route parameters and bodies. A non-2xx response still measures the server pipeline for that request shape; it is not a claim that the request was semantically valid.

There is no calibration pre-pass, no route-specific pre-warm, no excluded route and no budget exception. The only request before the measured request is the liveness check described above.

## Deployed Lambda — staging measurement, gate failing

The in-process gate does not include Lambda init, API Gateway, network or RDS. A separate read-only measurement records those on the only deployed backend:

```bash
MC_WRITE_DEPLOYED_LATENCY_REPORT=1 bash scripts/measure-deployed-latency.sh
```

The script verifies the AWS account, function and API integration; reads CloudWatch `REPORT` lines and API Gateway daily p99 metrics over 30 days; and makes three unauthenticated `GET /health/live` and `GET /health/ready` probes. It does not invoke the function directly, change configuration, deploy, or write user data. Cold starts are observed `Init Duration` values, not forced. While the result is failing it writes the report and exits **3**, so CI cannot treat the measurement as green.

Checked-in result (`deployed-latency-report.json`, measured 2026-11-03T15:30:24Z):

- Environment: **Staging** (`ASPNETCORE_ENVIRONMENT=Staging`); no separate production function exists, so **production p99 is unavailable**. The UI endpoint is the staging API.
- **4,244** REPORT invocations; p50 **100.76 ms**, p95 **5,976.87 ms**, p99 **6,895.20 ms**, max **27,000 ms**.
- **3,713** warm invocations; warm p50 **76.85 ms**, p95 **4,293.33 ms**, p99 **5,392.18 ms**, max **27,000 ms**.
- **531** observed cold starts; init p50 **1,239.47 ms**, p95 **1,439.95 ms**, p99 **1,667.85 ms**, max **2,100.01 ms**; cold request p99 **7,859.80 ms**, max **8,440.70 ms**.
- API Gateway daily p99: median **8,015.69 ms**, max **8,841.33 ms** across 16 one-day buckets.
- Current probe medians: `/health/live` **1,088.71 ms**, `/health/ready` **235.48 ms**; every probe returned HTTP 200.
- **Result: fail** against the 1000 ms diagnostic comparison. Warm p99 is also over budget, so cold start is not the sole cause; this is an open deployed performance defect, not a local-gate failure.

**Database is not the tail.** Over 14 days `AWS/RDS` for `musclecuties-staging-db` reports CPUUtilization max **50.9 %**, CPUCreditBalance held at **288**, ReadIOPS max **9.7**, DatabaseConnections max **14**, ReadLatency max **30 ms**. The instance is idle and unthrottled, so the historical 4 s tail is not database saturation.

**What remains unattributed.** The 30-day p99 of 6,895 ms was produced by code that had no route attribution, and the authenticated planner routes cannot be exercised without a synthetic account. The historical warm tail is therefore **not yet explained**; the new per-route telemetry and detailed metrics are what turn it into an attributable number on the next traffic window. No speedup of the authenticated planner is claimed here. Only two `Status: timeout` invocations exist in 30 days, both on 2026-10-19, so the tail is slow-completing work rather than hangs.

**Local gate caveat (important).** The in-process report's heavy routes short-circuit: `POST /api/v1/workouts/plan/strength-proposals` records `1.15 ms` with **HTTP 409** and the accept route `0.41 ms` with **HTTP 400**. Those numbers measure request validation, not plan generation, which is why a green local gate and a 5.4 s deployed warm p99 can coexist.

**Not verified by this deploy:** production (no production function or database exists), authenticated end-to-end planner latency, and the owner device pass.

## Limits

These are **in-process local numbers**. Lambda init, VPC/RDS Proxy connection setup, network round trips, API Gateway and S3 are outside this measurement. The separate deployed report covers Lambda/API Gateway on the only deployed backend (staging); it records a failing p99 and no production deployment. Neither report is a production SLA.
