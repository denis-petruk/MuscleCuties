## Set up Resend for the AWS Lambda backend

1. Sign in to [Resend](https://resend.com). In **Domains**, select `musclecuties.app` or add it to the correct Resend team. The repository sender is `MuscleCuties <noreply@musclecuties.app>`.
2. Public DNS has a `resend._domainkey` TXT key, `send` and `rsend` CNAMEs, and the new `_dmarc` TXT record. Resend shows the DKIM/SPF records as Verified and DMARC as healthy in Insights. Keep the single DMARC record and compare any future DNS changes with the exact values shown by your Resend team. Follow [Resend's domain instructions](https://resend.com/docs/dashboard/domains/introduction).
3. In **API Keys**, create a replacement key with **Sending access** restricted to that domain (rotating the key exposed during setup). Save it in a protected password manager when Resend displays it. [Resend documents key permissions](https://resend.com/changelog/new-api-key-permissions).
4. In the Lambda function running `MuscleCuties.Server`, open **Configuration → Environment variables**. Set `Resend__ApiKey` to that rotated key and `Resend__FromEmail` to `MuscleCuties <noreply@musclecuties.app>`. `RESEND_API_KEY` is a supported alternative key name. Save the configuration and publish the intended version or alias. Do not put the key in Git, `appsettings.json`, an IPA, a command line, or this chat. AWS encrypts Lambda environment values at rest but [recommends Secrets Manager for API keys](https://docs.aws.amazon.com/lambda/latest/dg/configuration-envvars.html). This code does **not** yet resolve Secrets Manager references automatically.
5. Use a synthetic test account with a real controlled mailbox to request a registration code and a password reset code. Confirm mailbox delivery, OTP verification, and RSA receipt issuance/validation. Inspect delivery status in Resend without copying recipient addresses or codes into application logs. This integration sends the recipient email and one-time code to Resend; it does not send health records. Reflect this processor and its retention policy in the privacy notice before real-user testing.

## AWS Lambda release controls

The [2026-10-29 implementation plan](infra/AWS_LAMBDA_POSTGRES_IMPLEMENTATION_PLAN.md) supersedes the older push-deployment description. The verified baseline was deployed through a **manual** GitLab job. Its Lambda code is ahead of the live PostgreSQL schema, so another code update is blocked until the database compatibility work and a reviewed recovery path are complete.

The implementation branch `infra/lambda-release-pipeline` adds mandatory source, backend, PostgreSQL fixture, mobile contract, package, and ARM64 checks before an artifact can be uploaded. A protected web pipeline can offer manual artifact upload and staging deployment jobs; those jobs do not constitute release authorization by themselves. The release tooling must reject an absent schema proof, lock owner, approved target, backup, artifact identity, or runtime verification. A successful Lambda update waiter is insufficient evidence of a successful release. Consult the [release checkpoint](infra/checkpoints/lambda-release-orchestrator.md) for which gates have actually run.

Before enabling a live staging release, the operator must verify the exact function/account/region/API/database binding, classify whether the target serves beta users, approve a dedicated immutable release bucket and OIDC role, scope AWS variables to the intended environment, provide an ARM64 runner, and prove the single PostgreSQL advisory-lock session is held across preflight, rollout, verification, report persistence, and recovery. The PostgreSQL implementation must supply the read-only `schema-preflight` and `schema-verify` contracts described in the checkpoint. Any `schema-reconcile` is a separate reviewed and authorized action; the pipeline must not replay unverified DDL.

The GitLab project was observed on **GitLab Free** on 2026-10-29. GitLab protected-environment deployment approvals require Premium or Ultimate, so the production deployment job remains disabled. An enforceable approval mechanism and an explicit integration change are required before production activation. The existing `AWS_ROLE_ARN` and `AWS_LAMBDA_FUNCTION_NAME` variables were observed as protected and masked but scoped to **All (default)**; protected merge request pipelines may receive protected variables under current project settings. Environment scoping and OIDC trust review are required before claiming validation jobs have no production credentials.

No artifact upload, Lambda deployment, API Gateway change, live database change, or authenticated smoke write was performed by the release-engineering implementation. The previous staging deployment role was documented with only `lambda:UpdateFunctionCode` and `lambda:GetFunctionConfiguration`; the new release process will need narrowly reviewed permissions for immutable S3 reads, guarded Lambda operations, and restricted reporting. Do not expand access solely to make a blocked job pass.

| `ConnectionStrings__PostgreSql` | Database operator's direct RDS PostgreSQL connection string, with verified TLS. Rotate the password exposed during setup before real-user use. The current deployment has no RDS Proxy. |
